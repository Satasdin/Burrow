Keeping a live AI session lean, and its memory whole

Claude Code fills its context with tool output, compacts, and then forgets the exact words. This plan says what Burrow will do at each step of a live session, what it cannot do from outside the model's path, and how we will prove it with real Claude Code runs. Mark it up. No code gets written until you approve.

What fills a session

Where the context goes

A coding session's window fills mostly with tool output: whole files, test logs, command output. The model needs a few lines of each and keeps all of it. Once the window is full, Claude Code rewrites the whole history into one summary. Everything said early is summarised again at every compaction, so it fades.

1. Lean output

When a Bash or Grep result is over about 6,000 characters, Burrow keeps the whole thing and the model sees the first and last 30 lines, every error line, and a handle such as k3f2a. A whole-file Read over about 1,500 lines (no range given) becomes the file's outline, its first 120 lines and a handle. burrow_expand k3f2a gives lines, a range or matching lines back.

Never shrunk: small output, reads that asked for a range, Edit and Write results, Burrow's own tools. Kept outputs live outside the vault, readable only by your account and only by the session that made them, the same rule as folds (D-105).

2. Automatic recall

On each new message, Burrow searches only what has left the context: kept outputs, this session's turns from before its last compaction, and earlier sessions' folds. Searching what the model can still see would only add noise. It hands back the exact words with their message reference, under 1,500 characters, and nothing at all when nothing matches well. It is marked as data, never as instructions.

3. Steered compaction new

At PreCompact, Burrow already makes a fold. It will also print short instructions for the summary: keep the person's requests and exact values word for word, name the kept-output handles and folds, and keep the open plan. This is the cheapest lever the research turned up.

4. A cache for the app's model

Measured today: Ollama reuses a prompt's start when it matches the last prompt exactly. A 4,600-token prompt went from 2.93 s to 0.05 s. Changing the window size reloads the model and loses the cache.

Today the app picks a different window per question and puts the parts that change first. The fix:

  • One fixed window per model, so the model is never reloaded.
  • Load it for 30 minutes.
  • Lay the prompt out with the parts that don't change first.
  • burrow chat keeps its history as an unchanged prefix.
  • Identical repeat questions get the kept answer.
  • Ollama's own count of cached tokens is recorded and shown.

What it can't do: Ollama has no way to save its cache to disk, so the cache can't outlive an unload. The llama.cpp shelf (D-60) stays for that.

5. Session panel

A new page in the app, one row per live or recent Claude Code session. It shows:

  • Context used over time, from the transcript's token counts.
  • Each compaction.
  • Outputs kept, with the characters they saved.
  • Folds made.
  • Recalls handed back, and whether the model then used the handle.

The hooks write a small meter file per session, and the panel reads it.

6. Connect and settings

burrow connect claude-code and hook install claude add the new entries: PostToolUse on Bash, Read and Grep; UserPromptSubmit; PostCompact. Each part can be switched off on its own. Nothing is written to your real ~/.claude/settings.json without asking you.

Resuming a session: fast and cheap

A resumed session has to be fed its whole history again. For Claude Code, that history is already in Anthropic's prompt cache for an hour after the last reply. For Burrow's own model, it is the model's working memory (its KV cache). Getting that memory back, instead of reading everything again, is what makes a resume fast and cheap.

7. Session cache for Burrow's own model

Today Ollama can't save its cache to disk, so a chat resumed tomorrow reads its whole history again. llama.cpp can, and it runs the model file Ollama has already downloaded, so nothing new is downloaded.

  • After each reply in burrow chat and the app's Ask, Burrow saves the conversation's cache.
  • On resume it loads the cache and reads only the new message.
  • The cache is filed by model and conversation, like the shelf (D-60), and cleared oldest first above a size limit.

Ollama remains the fallback when llama.cpp isn't installed.

8. Resume advice for Claude Code

On every resume, Burrow reads those numbers. When the cache has expired and the session is large, it shows you what the resume will cost to rewrite.

  • For example: "140,000 tokens, about $0.60."
  • It also offers the lean alternative: /clear, after which Burrow hands back this session's folds, plan and last request in about 6,000 tokens.

Lean output (part 1) also makes every resume cheaper, because there is less history to rewrite.

9. Keeping the cache warm your call

The fork result above means Burrow could send one tiny forked request shortly before the hour runs out. That keeps the cache alive while you're away.

  • Cost: on Sonnet 5.5, a cache read costs 0.05× and rewriting an expired hour-long cache costs 2×. One keep-warm request therefore costs about a fortieth of a rewrite.
  • Open question: I've only checked it from one headless session to another. Whether it matches an interactive session's cache needs one more test.

It would be off by default, with a limit you set.

Added 17 Nov from your idea

Resume any session, in any model, a month later

Burrow keeps every session on your Mac, or on an external SSD you choose: every word, every tool output and the kept outputs, indexed. Any program can pick it up. Claude Code, Codex, burrow chat on a local model, or the app.

  • The person types: /burrow:resume parser-fix in Claude Code, the same skill in Codex, or burrow session resume parser-fix.
  • The model gets: a small resume pack. Then it reads and recalls the rest from Burrow when it needs it.

What can and can't move between models

A prompt cache can't be shared between models. A cache is one model's working memory: the numbers its own weights made while reading those words. Anthropic's cache lives on Anthropic's servers for at most an hour, and no other model can read it. Qwen's cache means nothing to Gemma.

What moves is the words. So Burrow keeps the words whole and indexed. Each local model that resumes a session builds its own cache of the resume pack once, and Burrow keeps that cache on disk. From the second resume on, that model starts in under a second, as in part 7. Claude Code and Codex rebuild Anthropic's or OpenAI's cache from the small pack at a fraction of the full history's cost.

Storage, measured

Your Claude Code transcripts take 7.2 GB today, across 104 project folders. The largest single session is 203 MB, mostly tool output. Claude Code deletes transcripts after 30 days by default, so a session from a month ago is gone unless something keeps it.

Burrow's archive keeps them compressed; text usually shrinks 5 to 10 times. Local-model caches are the large part, so the archive folder can sit on an external SSD. If that drive is unplugged, the resume packs and the index still work from the Mac.

Codex both ways

Codex 0.146 is installed here and has skills, hooks and its own session files (~/.codex/sessions). Burrow has no Codex connection yet, so I'd add burrow connect codex. That gives MCP, the resume skill and its hooks, if they cover the same moments.

Burrow would also read Codex's sessions into the same archive, so a Codex session can be resumed in Claude Code and the other way round.

Privacy

Today the original messages go only to the program and session that wrote them (D-105). Resuming in another program changes that on purpose.

  • The resume pack, with secrets taken out, goes to the program you resume in.
  • The raw originals go there only after you approve that session for that program once, in the app or at the command line, the same way linked folders are approved.
  • A model asking on its own never gets another program's raw session.
Proof

How we will know it works

  1. The task. A scripted session of about 30 messages, run with real Claude Code in headless mode, on a scratch repository with big logs and long files. The first messages plant facts: a port number, an error code, a constraint the person states once. The window is set to Claude Code's floor of 100,000 tokens, so several compactions happen.
  2. Three arms, same script.
    • A: Claude Code alone.
    • B: Burrow 1.2.3 as shipped (folds only).
    • C: Burrow with every new part.
    Two runs per arm, if the cost is acceptable.
  3. Counted from the raw transcripts:
    • Compactions.
    • Context size after every request.
    • Tokens billed (input, cache read, cache write).
    • Outputs kept and expanded.
    • Recalls handed back.
  4. The quiz. At the end, 8 questions about the early part of the session, each with one right answer, graded exactly. A failed answer is reported as plainly as a right one.
  5. The app's model. The same 10 questions asked twice in burrow chat and in the app, before and after the change. We record seconds to the first word, the cached tokens Ollama reports, and whether the answers stay the same.
  6. Every transcript, hook log and number goes into docs/evidence/session-context/ on the branch. swift test is run in full and the whole log read; the app is rebuilt.

One setup note. A scratch HOME isn't logged in to Claude Code, because the login lives in your keychain. The runs therefore use your login and switch off your own settings and MCP servers (--setting-sources project,local --settings scratch.json --strict-mcp-config), so your real Burrow hooks don't fire. I checked this today: a test session saw no Burrow context. Claude Code still writes those runs' transcripts under ~/.claude/projects, in folders named after the scratch directory.
